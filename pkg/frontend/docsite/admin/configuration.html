Configuration

Each serve flag has an environment variable. A flag on the command line overrides the variable. The same holds for serve web and serve api, the two processes of a split deployment. serve body is the body service, a third kind of process.

Flag Environment variable Default Description
--listen DEXAFIX_LISTEN :8080 Address to listen on for plain HTTP. For serve api, the public API instead.
--db-driver DEXAFIX_DB_DRIVER sqlite sqlite or postgres.
--dsn DEXAFIX_DSN file:dexafix.db Database connection string. A string with a password is refused on the command line: use the variable or --dsn-file.
--dsn-file DEXAFIX_DSN_FILE empty File holding the connection string.
--auto-migrate DEXAFIX_AUTO_MIGRATE true Apply pending migrations on startup; when false, serve fails if any are pending.
--force-password-login DEXAFIX_FORCE_PASSWORD_LOGIN false Keep password sign-in on, to recover from a lockout.
--encryption-key-file DEXAFIX_ENCRYPTION_KEY_FILE dexafix.key Key file for encrypted values. Created if missing, but only for a database without encrypted values.
(none) DEXAFIX_ENCRYPTION_KEY unset Key itself, overrides the key file. No flag.
--encryption-key-previous-file DEXAFIX_ENCRYPTION_KEY_PREVIOUS_FILE empty File with earlier keys, one per line, for a key rotation.
(none) DEXAFIX_ENCRYPTION_KEY_PREVIOUS unset Earlier keys, comma separated, for a key rotation. No flag.
--backend-url DEXAFIX_BACKEND_URL empty serve web only. Required: the internal address of the api process, such as http://api:8081.
--service-secret-file DEXAFIX_SERVICE_SECRET_FILE empty serve web, and serve api when the internal listener is on. Required there. The shared secret, see Split deployment.
--worker-secret-file DEXAFIX_WORKER_SECRET_FILE empty serve api when the internal listener is on, and serve worker. Secret of one provider's workers; must differ from the service secret. On serve api it is PROVIDERS=FILE, repeated once for each provider (variable DEXAFIX_WORKER_SECRET_FILES, entries separated by ;), and a secret opens that provider's jobs only.
--internal-listen DEXAFIX_INTERNAL_LISTEN :8081 serve api only. Internal API for the web process; keep it on a private network. Empty turns it off.
--maintenance DEXAFIX_MAINTENANCE true serve api only. Runs the audit log purge and certificate renewal. Turn it off on all but one api process.
--api-upstream DEXAFIX_API_UPSTREAM empty serve web only. Passes /api/ on to the api process's public listener, for setups without a proxy that routes by path. Off by default.
--internal-tls-cert-file DEXAFIX_INTERNAL_TLS_CERT_FILE empty serve api only. Server certificate of the internal listener. Set it with --internal-tls-key-file and --internal-tls-client-ca-file, or none. See Mutual TLS.
--internal-tls-key-file DEXAFIX_INTERNAL_TLS_KEY_FILE empty serve api only. Private key of the certificate above.
--internal-tls-client-ca-file DEXAFIX_INTERNAL_TLS_CLIENT_CA_FILE empty serve api only. CA that issues the certificates of the web process. The internal listener then requires a client certificate from it.
--backend-ca-file DEXAFIX_BACKEND_CA_FILE empty serve web only. CA that must have issued the certificate of the api process. Use with an https:// --backend-url. See Mutual TLS.
--backend-client-cert-file DEXAFIX_BACKEND_CLIENT_CERT_FILE empty serve web only. Client certificate that web presents to the api process.
--backend-client-key-file DEXAFIX_BACKEND_CLIENT_KEY_FILE empty serve web only. Private key of the client certificate above.
--backend-server-name DEXAFIX_BACKEND_SERVER_NAME empty serve web only. Name the api process's certificate must carry, if it is not the host of --backend-url.
--body-url DEXAFIX_BODY_URL empty serve api only. Address of a body service in its own process, such as http://body:8082. Empty runs the body service inside the api process.
--body-secret-file DEXAFIX_BODY_SECRET_FILE empty serve api with --body-url, and serve body. Secret they share, one per line (the api process sends the first, the body service accepts every line). Must differ from the service and worker secrets.
--body-token-key-file DEXAFIX_BODY_TOKEN_KEY_FILE empty serve api with --body-url. Private key that signs the tokens for the body service (secrets body-token-key).
--body-ca-file DEXAFIX_BODY_CA_FILE empty serve api only. CA that must have issued the body service's certificate. Use with an https:// --body-url, together with the two files below.
--body-client-cert-file DEXAFIX_BODY_CLIENT_CERT_FILE empty serve api only. Client certificate that the api process presents to the body service.
--body-client-key-file DEXAFIX_BODY_CLIENT_KEY_FILE empty serve api only. Private key of the client certificate above.
--body-server-name DEXAFIX_BODY_SERVER_NAME empty serve api only. Name the body service's certificate must carry, if it is not the host of --body-url.
--listen (serve body) DEXAFIX_BODY_LISTEN :8082 serve body only. Address of the body service; keep it on a private network.
--health-listen DEXAFIX_HEALTH_LISTEN empty (off) serve api, serve body and serve worker. A listener that answers /healthz and /readyz only, for a container health check, such as 127.0.0.1:8083. See Status and health checks.
--pprof DEXAFIX_PPROF off serve api, serve body and serve worker. Also serves Go profiling data under /debug/pprof/ on the --health-listen listener, which must then be a loopback address (the process refuses to start otherwise). See Profiling.
--valkey-url DEXAFIX_VALKEY_URL empty (off) serve api only. Keep the failed sign-in counters, single-use values and sessions in Valkey (redis://host:6379/0, rediss:// for TLS) instead of the database. A password in the URL is refused on the command line: use the file. See Valkey.
--valkey-url-file DEXAFIX_VALKEY_URL_FILE empty serve api only. File with the Valkey URL, which may hold the password: redis://:password@host:6379/0.
--body-token-public-key-file DEXAFIX_BODY_TOKEN_PUBLIC_KEY_FILE empty serve body only. Required. Public key(s) of the api process's token key, one per line (secrets body-token-public).
--body-tls-cert-file DEXAFIX_BODY_TLS_CERT_FILE empty serve body only. Serve over mutual TLS: certificate of the service. Set it with --body-tls-key-file and --body-tls-client-ca-file, or none.
--body-tls-key-file DEXAFIX_BODY_TLS_KEY_FILE empty serve body only. Private key of the certificate above.
--body-tls-client-ca-file DEXAFIX_BODY_TLS_CLIENT_CA_FILE empty serve body only. CA that issues the api process's client certificate.
--without-body DEXAFIX_WITHOUT_BODY false serve api (needs --body-url) and the db, user and settings commands. This database does not hold the scale readings and DEXA scans because a body service of its own does; keeps the commands from creating their tables here.

serve body takes the database and key flags too, for the database and key of the body service. It has no --maintenance, and its --auto-migrate migrates the body database only.

serve web has no database and no encryption key, so it has no database or key flags. If DEXAFIX_DSN_FILE or DEXAFIX_ENCRYPTION_KEY is set for it, it logs a warning and ignores the variable. The database and key flags belong to serve api.

DEXAFIX_FORCE_PASSWORD_LOGIN counts as set only when it is exactly true. 1 or TRUE leaves it off.

Settings on the Admin page

Some settings are not flags. They are stored in the database, encrypted like the other settings, and take effect at once, without a restart. Administrators change them on the Admin page:

  • Network and retention
    • Base URL, such as https://dexa.example.com. Empty by default.
    • Trusted proxies. Empty by default, which trusts nobody. See Running behind a reverse proxy.
    • Accept the PROXY protocol from the trusted proxies. Off by default. See PROXY protocol.
    • Allow sign-in providers on private network addresses. Off by default. See Outgoing connections.
    • Allow the mail server on a private network address. Off by default, and separate from the one for providers.
    • Upgrading: a sign-in provider or mail server that runs on a private address (10.x, 172.16.x–172.31.x, 192.168.x, 100.64.x, fc00::/7) stops working until you turn on the setting for it; password sign-in keeps working, so you can still reach the Admin page.
    • Keep the audit log for N days. 365 by default; 0 keeps it forever.
    • Remind me to rotate the encryption key after N days. Empty or 0 never reminds. Rotation stays manual.
  • E-mail: SMTP server, port (587 by default), encryption (starttls by default, tls, or none for a server on localhost only), user name, password (stored encrypted, never shown again) and sender address. See Password reset.
  • HTTPS, HTTP/2 and HTTP/3: certificate, HTTPS port (8443 by default) and HTTP/3. Plain HTTP stays on --listen. See HTTPS, HTTP/2 and HTTP/3.
  • Analytics and ads: off by default. A Scarf pixel ID (a UUID), a Google Analytics measurement ID (G-…) and a Google AdSense publisher ID (ca-pub-…). When one is set, a visitor who is not signed in is asked, on the sign-in page, the documentation, the status page and the terms and privacy pages, whether to accept it. Nothing is loaded from Scarf or Google before they press Accept, signed-in people never get it, and the footer's Privacy choices reopens the question. The sign-in page never offers AdSense (it widens the script policy to inline scripts, and the page asks for passwords), only Scarf and Google Analytics. On those pages the content security policy allows the hosts of the services that are on; AdSense also needs inline scripts and images from any HTTPS address, so turn it on only if you accept that. The privacy policy (/privacy in the app) describes it to visitors. Below those fields, an ads.txt text box is served publicly at /ads.txt on the site root (404 while empty); ad networks such as AdSense look for it there, so the app must be served at the root of its host. It loads nothing for visitors and needs no consent. The ad wiring follows Google's published requirements and has not been tried against a live AdSense account.

There are no flags or environment variables for these settings, and none for SMTP. If DEXAFIX_TRUSTED_PROXIES, DEXAFIX_BASE_URL or DEXAFIX_AUDIT_RETENTION_DAYS is still set, the server logs a warning that it is ignored. If a wrong base URL or PROXY protocol setting locks you out, see Settings recovery.

The remaining flags are the ones the server needs before it can open the database: the listen address, the database, the encryption key and --auto-migrate.

  • LOGLEVEL sets the log level: trace, debug, info, warn, error, fatal or panic. The default is info.
  • LOGFORMAT sets the format of the log on stdout: console (the default, readable lines) or json (one JSON object per line, for a log collector, with time, level, message and, for serve, service and the fields of the event).
  • Colour and the short time of day are used only when stdout is a terminal, so docker logs and files stay plain. NO_COLOR (any value) or DEBUG (any value) turns the colour off on a terminal too; neither changes the log level.

Every process says which one it is. A line of serve api looks like this, and the combined dexafix serve has no prefix:

2026-11-10T11:39:12Z INF api │ serving the backend db=postgres internal=:8081 public=

The banner (DexaFix 1.2.3 · api) goes to stderr, in the console format only, and a process logs shutting down and stopped when it is stopped by a signal. In the Compose file Docker keeps at most three files of 10 MB per container.

Postgres example:

export DEXAFIX_DSN=postgres://user:pass@localhost/dexafix
go run . serve --db-driver postgres

Secrets are never accepted as command-line flags, because other users of the machine can read them with ps and shells keep them in their history. A connection string with a password comes from the environment or from a file (--dsn-file, --from-dsn-file, --to-dsn-file, --admin-dsn-file, or the matching DEXAFIX_*_FILE variables), which works well with Docker and Kubernetes secrets. A plain --dsn file:path.db without a password is fine. Passing a password in a flag makes the command fail with a message that says so. The encryption key has no flag either (see Encryption).

dexafix info prints information about the binary.
