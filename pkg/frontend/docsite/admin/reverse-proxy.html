Running behind a reverse proxy

DexaFix speaks plain HTTP. For HTTPS, put a reverse proxy such as nginx, Caddy or Traefik in front of it, and bind DexaFix to a private address so that nobody can bypass the proxy: --listen 127.0.0.1:8080. DexaFix can also serve HTTPS itself, see HTTPS, HTTP/2 and HTTP/3.

A proxy hides two things from the app: who the visitor is (every connection comes from the proxy) and whether they used HTTPS. The proxy passes both on in the X-Forwarded-For, X-Forwarded-Proto and X-Forwarded-Host headers. Any visitor can send those headers too, so DexaFix only believes them on connections from the trusted proxies. From everyone else they are ignored, and a warning is logged once.

Trusted proxies and base URL

Both are set on the Admin page, under Network and retention. They are stored in the database, not in flags, and take effect at once without a restart.

Setting What it does
Trusted proxies Comma-separated addresses or CIDR ranges of your proxies, such as 127.0.0.1,10.0.0.0/8. The keyword loopback stands for 127.0.0.0/8 and ::1; private adds the RFC 1918 ranges and fc00::/7. Empty trusts nobody.
Base URL The public address, scheme and host only (no path), such as https://dexa.example.com. Optional when the proxy forwards Host and X-Forwarded-Proto correctly; set it for a fixed, predictable address. Saving it is accepted only while you use that address, so a typo cannot lock you out.

What changes when the proxy is trusted:

  • Sign-in limits and the audit log use the visitor's address. Without this, everyone shares the proxy's address: one person's failed sign-ins would block everybody, and the audit log would show only the proxy.
  • Cookies are marked Secure and Strict-Transport-Security is sent, as soon as the visitor used HTTPS (as reported by the proxy), or the base URL is https.
  • Sign-in provider callback URLs (the ones to register at your identity provider, shown on the Admin page) are built from the base URL, or else from X-Forwarded-Proto and the host.
  • Form posts pass the same-origin check. The browser's Origin has to match the host it visited, which is why the proxy must pass the original host, either as Host or as X-Forwarded-Host, or you set the base URL.
  • Passkeys need HTTPS in the browser, and belong to the host name the browser uses. Behind a proxy that terminates TLS, set an https base URL. See Passkeys.

For the address, the app reads X-Forwarded-For from the right: it skips every address that belongs to a trusted proxy, and the first address after that is the visitor. Anything the visitor wrote further left is never used. Make sure the proxy appends to this header instead of passing along what the client sent. Without X-Forwarded-For, X-Real-IP is used.

Examples

Examples, assuming DexaFix listens on 127.0.0.1:8080 on the same machine:

# nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

# Caddy: forwards the headers by default
dexa.example.com {
    reverse_proxy 127.0.0.1:8080
}

# Traefik (docker labels)
traefik.http.routers.dexa.rule=Host(`dexa.example.com`)
traefik.http.routers.dexa.tls=true
traefik.http.services.dexa.loadbalancer.server.port=8080

On the Admin page, set Trusted proxies to loopback and Base URL to https://dexa.example.com, then start DexaFix with:

dexafix serve --listen 127.0.0.1:8080

In Docker, the proxy reaches the app from the network's bridge address, so use the network's range, or private. Only trust ranges that nothing but your proxies can send from.

DexaFix must be served from the root of its host. A sub-path such as example.com/dexa/ is not supported. If you use Withings, the redirect URL on the Admin page has to be the public callback address, for example https://dexa.example.com/integrations/withings/callback.

PROXY protocol

The PROXY protocol (HAProxy versions 1 and 2) passes the visitor's address on the TCP connection itself, before any HTTP. Use it with a balancer that works at TCP level and adds no X-Forwarded-For header.

Turn on Accept the PROXY protocol from the trusted proxies on the Admin page. It needs trusted proxies. With it on:

  • A connection from a trusted proxy may start with the header. The address in it becomes the visitor's address. The header is optional there, so a balancer that does not send it cannot lock anyone out.
  • A connection from any other address may not start with the header. It is refused, so nobody can claim an address.
  • With the setting off, connections pass through untouched.

It applies to the plain and the HTTPS listener, and to each new connection at once. The header does not say whether the visitor used HTTPS, so set an https base URL to get Secure cookies.

HAProxy terminates TLS and sends the address with send-proxy-v2:

# haproxy.cfg
frontend dexa
    mode http
    bind :443 ssl crt /etc/haproxy/dexa.pem
    http-request set-header X-Forwarded-Proto https
    default_backend dexa

backend dexa
    mode http
    server dexa 127.0.0.1:8080 send-proxy-v2

An AWS Network Load Balancer works at TCP level and adds no headers. Use a TCP listener on port 443, forward it to a target group on port 8443 (the HTTPS port of DexaFix, with a certificate you upload on the Admin page), and turn on Proxy protocol v2 for the target group. Trusted proxies must cover the addresses the load balancer connects from, for example your VPC range.

nginx passes TCP through with the stream module and sends the address with proxy_protocol on:

# nginx.conf, stream context
stream {
    server {
        listen 443;
        proxy_pass 127.0.0.1:8443;
        proxy_protocol on;
    }
}

Here DexaFix serves HTTPS on port 8443 and trusts loopback.

HTTPS, HTTP/2 and HTTP/3

DexaFix can serve HTTPS itself. Behind a reverse proxy you usually leave this off and let the proxy terminate TLS. Plain HTTP stays on the --listen port, with HTTP/1.1 and cleartext HTTP/2 (h2c, with prior knowledge) for proxies that speak it to the backend.

Set it on the Admin page, under HTTPS, HTTP/2 and HTTP/3:

  • Certificate: either upload a PEM certificate chain and a PEM private key, or let DexaFix generate a self-signed certificate. An uploaded key is stored encrypted and is never shown again. Leave both fields empty to keep the saved certificate.
  • A self-signed certificate is ECDSA P-256, valid 365 days, and renewed automatically 30 days before it expires. Its names are the names you give, or else the base URL's host plus localhost, 127.0.0.1 and ::1.
  • HTTPS port: 8443 by default. It must differ from the plain HTTP port. HTTPS runs on its own listener, so a bad certificate or port cannot lock you out of the plain one. HTTP/2 and HTTP/1.1 are offered by ALPN on TLS 1.2 and later.
  • Also serve HTTP/3 (QUIC): runs on the UDP port with the same number as the HTTPS port, and is advertised to HTTPS clients with an Alt-Svc header. The UDP port must be reachable.

The Admin page shows the certificate names, expiry, SHA-256 fingerprint and any bind error.

With Docker, publish both ports, and the UDP one for HTTP/3:

docker run -p 8080:8080 -p 8443:8443 -p 8443:8443/udp -v dexafix-data:/config ghcr.io/trueforge-org/dexafix:latest

Browsers and apps trust a self-signed certificate only once you add it to their trust store, and browsers use HTTP/3 only with a trusted certificate. There is no redirect from HTTP to HTTPS yet.

Passkeys belong to the address you open, port included. Use the HTTPS address for them, such as https://dexa.example.com:8443, and not the plain HTTP one.

Behind a CDN or caching proxy

Everything DexaFix serves except /static/ is personal: pages, exports, the JSON API and error pages. Every such response carries Cache-Control: no-store, CDN-Cache-Control: no-store and Surrogate-Control: no-store. The last two speak to CDNs such as Cloudflare, Fastly and Akamai directly. The one exception is the estimates endpoint of the API, which sends Cache-Control: private, no-cache with an ETag, so a browser may keep a copy and ask whether it is still good, while a shared cache may not keep it. A test (cache_test.go) checks this on pages, redirects, errors and the API, and that /static/ lists no directory.

Only /static/ files with a ?v= version may be cached for long. They hold no personal data.

A CDN rule can override an origin's headers. A rule such as Cloudflare's Cache Everything with an Edge Cache TTL that overrides the origin would serve one visitor's page to another. To be safe:

  • Cache /static/* only, and bypass the cache for everything else. Do not use Cache Everything on the whole site.
  • Do not let a rule override the origin's cache headers for paths other than /static/*.
  • Do not use a page-cache feature on a site that has sign-in.

I have not tested this against a real CDN account; the headers and the test above are what the code does.

For the visitor's address, add the CDN's address ranges to Trusted proxies (Cloudflare publishes its list at https://www.cloudflare.com/ips/). DexaFix then walks X-Forwarded-For from the right, past every trusted proxy, and takes the first address nobody trusted. A visitor cannot make up their address that way, and a request that reaches the origin directly, not through the CDN, has its X-Forwarded-* headers ignored. Without the CDN's ranges in the list every visitor looks like the CDN, and the limit on failed sign-ins per address (60 in 15 minutes) would lock out everybody together.

Two processes: path split

With the split deployment, the proxy sends /api/ to the api process's public listener and everything else to the web process. Both must see the proxy as trusted. Set Trusted proxies once on the Admin page: it is stored in the database, so it applies to both processes.

The examples assume the web process listens on web:8080 and the api process on api:8080, for example on one Docker network:

# nginx
location /api/ {
    proxy_pass http://api:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

location / {
    proxy_pass http://web:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

# Caddy
dexa.example.com {
    handle /api/* {
        reverse_proxy api:8080
    }
    handle {
        reverse_proxy web:8080
    }
}

# Traefik (docker labels on the api service)
traefik.http.routers.dexa-api.rule=Host(`dexa.example.com`) && PathPrefix(`/api/`)
traefik.http.routers.dexa-api.tls=true
traefik.http.services.dexa-api.loadbalancer.server.port=8080

# Traefik (docker labels on the web service)
traefik.http.routers.dexa-web.rule=Host(`dexa.example.com`)
traefik.http.routers.dexa-web.tls=true
traefik.http.services.dexa-web.loadbalancer.server.port=8080

# haproxy.cfg
frontend dexa
    mode http
    bind :443 ssl crt /etc/haproxy/dexa.pem
    http-request set-header X-Forwarded-Proto https
    http-request set-header X-Forwarded-For %[src]
    use_backend dexa_api if { path_beg /api/ }
    default_backend dexa_web

backend dexa_api
    mode http
    server api api:8080

backend dexa_web
    mode http
    server web web:8080

The path split needs a proxy that reads the path, so it must terminate TLS. If the web process serves HTTPS itself, a proxy that only passes TCP cannot split the paths. Then set DEXAFIX_API_UPSTREAM on the web process instead, and see Split deployment.
